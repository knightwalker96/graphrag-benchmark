Section 1Request flow — question string in, answer and citations out

The spine is short and fixed: load once, reset the live-query counter, route, run exactly one branch, assemble context, make one generator call, record metrics. Everything that varies between questions happens inside the branch, and every branch converges on the same prompt builder — which is what keeps the token comparison with Basic RAG a comparison of context, not of plumbing.

Per-route token and strict-pass figures are the by_gold_route block of summary.json (20 questions per route, route-balanced). temporal at strict 0.00 is reported as measured, not rounded away — it is the one route whose token win did not buy accuracy.

1.2 · The aggregation branch — seven resolvers, one intersection

This is the branch where graph structure does work vector retrieval cannot: enumerating every company that satisfies a typed constraint. The constraint detector deliberately does not break early, so a question carrying two constraints produces two company sets that are intersected on normalised tickers.

1.3 · Bridge and compare — the same hop, two different payloads

Both branches resolve something from the graph and then need a second fact. Bridge resolves an entity and reads curated edges off it; compare resolves two companies and mines one statement row from each. Both keep a chunk-retrieval fall-back so a half-resolved question is never answered from half the evidence.

1.4 · The lookup / temporal / default cascade — replace, don't append

One branch serves three route labels through four ordered attempts. The governing rule is the optimization change: when a deterministic artifact answers the question, it replaces the retrieved context instead of being appended to it. A resolved flag carries that decision forward, and a compound question — one asking for two distinct facts — is the single case where appending is still correct.

Section 2The router — seven gates, first match wins

The router is a pure function of the question string: no corpus read, no embedding, no model call, which is why optimizer_tokens is zero. It is also the one component whose correctness depends on order, because several routes share a sentence opening. Two gates are guarded by conjunctions so that a broader pattern below them stays untouched.

Two ablation hooks sit above gate 1 and are shown in figure 1.1: P3_ROUTE_FORCE replaces the whole chain with a fixed or md5-seeded random label while leaving every branch live, and P3_ROUTER_OFF returns "default", which no branch matches — disabling routing, graph traversal and compression together.

Section 3Context assembly — four ways to fill the same prompt slot

Every branch ends at the same place: a context string and a list of citation ids. What differs is how much of the corpus survives into that string. All four assemblers below are deterministic string work — no model call, no embedding call — so moving between them changes what the generator reads without changing what the pipeline is charged for producing it.

Section 4Data and index layer — what exists, and who reads it

Three stores sit behind the branches, and they are not interchangeable. The local provenance index holds the evidence sentences that make compression citable; the graph holds the typed structure that makes enumeration possible and supplies the vector search; Chroma serves the Basic RAG baseline and is never read by Pipeline 3. Building the graph cost tokens once; answering a question costs none of them.

Section 5The Olympics pipeline — same machine, different lexicon

The second dataset re-uses the architecture deliberately and keeps every dataset-specific decision in two files. The question shapes are different — six routes, not five, with a superlative route the SEC set has no analogue for — but the spine is the same: route, run one branch, compress to evidence rows, make one generator call, record the hop log.

5.2 · Portable mechanism versus swapped lexicon

The claim this split is designed to test: the mechanism transfers and the lexicon does not. The evidence is in section 2's measured panel — the SEC router scores 0.800 in domain and 0.173 on Olympics questions, labelling 100% of them lookup. A third dataset therefore needs one new lexicon file, not a new pipeline.

Shared — carried over unchangedthe portable mechanism

  • Per-question live-graph counter. _tg_query_count reset in run_single, tg_live derived from it. The session-level version overstated live-graph use and was removed.
  • The un-confounded ablation hook. P3_ROUTE_FORCE degrades only the label; P3_ROUTER_OFF is kept so the confounded arm stays comparable.
  • Fail-loud connection. P3_REQUIRE_TG raises rather than letting a suspended instance look like a degraded local run.
  • Evidence-sentence substitution and the MAX_CTX_CHUNKS × MAX_CTX_CHARS budget both pipelines share with the baseline.
  • One generator call, shared prompt, shared token accounting — graph_doc_ids, optimizer_tokens, preserve_answer.

Swapped — one lexicon, one schemawhat a third dataset would write

  • Question patterns. Five Olympics regexes against eight SEC ones; a superlative route with no SEC analogue, and no bridge or compare route because this corpus asks neither shape.
  • Vertex and edge vocabulary. Games / Event / Venue / Nation / Athlete / Sport against Entity / Chunk, and games_precedes in place of the curated finance relations.
  • Key normalisers. norm_date and norm_venue exist because the questions quote infobox strings verbatim, concatenations included.
  • How the graph is built. Gemini extraction on SEC; deterministic infobox regex on Olympics, at zero LLM tokens and reproducible from the corpus.
  • What the honest claim is. All 150 Olympics questions come from five rigid templates, so a near-perfect router here is a weak result and belongs in the table only as the in-domain control for the 0.173 collapse.
